## 专项：对接真实外部 WireGuard 出口节点（端到端验收）

在一台**完全可控**的云服务器（腾讯云 ECS，Ubuntu 22.04）上，用用户自研工具
WarpPool 部署的出口节点做了一次完整验收。这是第一次在**不受干扰**的环境里
把"客户端 → WireGuard → 公网出口"整条链路走通。

客户端配置（服务端 `wpnat` 接口，监听 `0.0.0.0:51820`）：

```ini
[Interface]
PrivateKey = <本机私钥>
Address    = 10.200.0.4/32

[Peer]
PublicKey  = <服务端公钥>
Endpoint   = 142.86.118.134:51820
AllowedIPs = 0.0.0.0/0, ::/0        # 全隧道
PersistentKeepalive = 25
```

| 检查项 | 结果 |
|---|---|
| 密钥对自洽（私钥推导公钥） | ✅ 与配置给出的公钥一致 |
| 服务端确认 | ✅ `wg show`：peer 已登记、`latest handshake: 10 seconds ago`、有收发字节 |
| **直连**握手 + 出网 | ✅ 出口 IP = `142.86.118.134`（服务端公网 IP） |
| **经前置代理 前置**握手 + 出网 | ✅ 出口 IP 同上 |
| 四个独立来源核对出口 IP | ✅ ifconfig.me / api.ipify.org / ip-api.com / cloudflare trace 全部一致 |
| 真实网站访问 | ✅ example.com、bing.com 正常返回 |
| SOCKS5 与 HTTP 两种客户端 | ✅ 均可用（mixed 协议） |
| 延迟 | 直连 1.23s → 经隧道 0.62s |

结论：**ChainProxy 的 WireGuard 实现在真实公网出口上完全可用**，
`0.0.0.0/0` 全隧道、`endpoint` 走公网直连、以及"经前置代理"两种前置方式都通过。

> 之前对另一台共享服务器（`204.197.163.238:31496`，NAT 映射到容器内）反复失败，
> 表现为"握手包发出（`tx_bytes=444`）、零回包（`rx_bytes=0`）"。
> 换成这台可控服务器后一次通过 —— 说明**问题在那台服务器的 NAT/网络环境**，
> 与客户端实现无关。共享节点上"其它 peer 持续有流量"也印证了该环境不适合排障。

### 那台服务器的根因（后来拿到 root，已定位到最后一步）

**结论：`204.197.163.238:31496` 的 TCP 转发正常，UDP 转发不生效 ——
尽管服务商面板里该条目写的是 "TCP/UDP"。**

| 检查 | 结果 |
|---|---|
| 容器内 WG | ✅ `wp1` 正常监听 `0.0.0.0:51820`（UDP），我方 peer 已登记、allowed IPs 正确 |
| **TCP `31496`（容器内开 TCP 监听在 51820）** | ✅ **连通**、数据双向正常 |
| **UDP `31496`（抓全部 UDP，不过滤端口）** | ❌ 来自客户端的包**一个都没到**（只有主服务器 peer 的握手与 WARP 的 IPv6 流量） |
| `wpls list` 节点自查 | 两个 `wg` 条目端口 `31496`、状态**从未握手**；主服务器 peer（内网 `51820`）**在线** |

**=> UDP 侧的转发在实际链路上没有生效。** 需要在服务商侧排查
（面板显示与实际规则不一致、或该 UDP 条目指向了别的内部地址）。

> ⚠️ **一次方法论教训**：我最初在容器上开 UDP 监听在 `31496` 去等，
> 但**如果映射是 `31496 → 51820`，包会被转发到 51820**，监听 31496 永远收不到。
> 那次测试是无效的（结论碰巧正确，但方法不成立）。
> **可靠的验证方式是在容器上抓包（`tcpdump -ni eth0 udp`，不加端口过滤），
> 同时从外部发包** —— 这样无论映射指向哪个端口都能看到。

### 为什么"主服务器能跑流量"却不需要配端口映射

容器有两个地址，主服务器走的是**另一条不需要映射的路**：

| 地址 | 性质 | 谁能连 |
|---|---|---|
| `172.16.233.90` | 容器的**直连地址** | 机房网络（主服务器 `64.90.17.152`、其它机房）✅；家宽 ❌ |
| `204.197.163.238` | **NAT 网关**的公网地址 | 任何人，但必须有端口映射 |

证据：抓包里主服务器的包是 `64.90.17.152.40835 > 172.16.233.90.51820`
—— **目的地址是容器的直连地址、源地址未被改写，说明是纯路由、完全没经过 NAT**。
反过来，从家用宽带打 `172.16.233.90:51820` 时包在中间就被丢了
（`172.16/12` 属 RFC1918，很多运营商边缘做 bogon 过滤；机房网络通常不过滤）。

**所以"主服务器走同一个端口也没配映射"不是矛盾 —— 它压根没走那层 NAT。**

## 技术选型的为什么

### 为什么内嵌 sing-box **库**，而不是拉起一个外部 core 进程

- **单文件分发**：产物就是一个 `chainproxy-cli.exe`，不用另外附带 core 的二进制、也不用给它准备配置目录。
- **生命周期一致**：出口跟着节点启停，进程退出就一起回收，不会留下孤儿 core 进程，也不需要自己写"生成配置 → 启动 → 探活 → 重启"的进程管理。
- **少一跳**：`internal/engine` 直接拿到 `adapter.Outbound` 调 `DialContext` / `ListenPacket`，
  不需要"本地再开一个 socks 入口、再连它"——那会多占一个端口、多一次转发。
- **依赖不扩散**：`internal/proxy` **不 import** sing-box，而是通过
  `proxy.RegisterSingBoxFactory(...)` 注册（`internal/engine/register.go` 的 `init`）。
  于是 `internal/proxy` 的单元测试不需要编译整个 sing-box。

### 为什么不自己实现那 5 种协议

那 5 种各自带着一套密码学与帧格式（VMess 的 AEAD 头、VLESS 的 uTLS/Reality、
Shadowsocks 的 2022 系列、Trojan 的 TLS 伪装、Hysteria2 的 QUIC），自己实现等于重造一个
sing-box，而且没有任何官方测试向量可依。

自研的 3 种（socks5 / http / wireguard）之所以自研，是因为它们足够简单，
而且我们要的是"能挂前置、能统计流量、能半关闭中继"这层控制权。

复用 sing-box 还有个额外收益：它**严格解析配置**（未知字段直接报错），
所以"配置能被它接受"本身就是一条有约束力的断言 —— 见 `TestParseStrictnessIsReal`。

### 为什么圈选窗口是纯 Win32，而不是第二个 Webview

**Wails v2 没有多窗口 API**（`options.App` 描述的是唯一那个窗口）。
而圈选要求在"无边框 + 全屏置顶 + 隐藏系统光标 + 自画十字准星"的前提下工作，
直接用 `WS_POPUP + WS_EX_TOPMOST` 反而更省事：

- **先截图、再建窗口** —— 否则会把圈选窗口自己拍进底图，变成"套娃"；
- **红色十字准星由自己在 `WM_PAINT` 里画**（1 像素、贯穿客户区），
  不做 `CreateCursor` 自定义光标位图 —— 那套 API 在 DPI 缩放 / 多屏下很脆；
- 光标用 `ShowCursor(FALSE)` 隐藏，并在任何退出路径（正常结束、报错、panic）都恢复。

## 关键技术验证结论（全部实测得出）

这些结论在写代码之前先用 `.cache/spike-singbox` 验证过，之后固化成
`internal/engine/singbox_test.go` 里的测试：

| 结论 | 表现 | 处理 |
|---|---|---|
| 必须 `include.Context` | 否则反序列化报 `missing outbound options registry in context` | 每个实例用一个**新的** ctx（`box.New` 会往 ctx 里注册本实例的 Manager，共享会互相覆盖） |
| 必须带构建标签 | 否则运行时报 `uTLS, which is required by reality is not included in this build` | 统一 `-tags "with_utls,with_quic"`；并加 `BuildCheck()` 把运行期错误提前成一句明确的话 |
| 取出口要用 `inst.Outbound().Outbound(tag)` | `adapter.Router` 上没有 `Outbound` 方法 | 见 `internal/engine/singbox.go` |
| `direct` 出口不允许 `detour` | 报 `'detour' is not supported in direct context` | 直连模式**完全不生成**前置出口，也不写 detour |
| `transport.type` 没有 `tcp` | 只能取 http / ws / grpc / quic / httpupgrade | 网络为 tcp 时**整个 transport 字段都不写** |
| `transport.host` 类型不统一 | http 是数组、httpupgrade 是字符串、ws 走 headers | 分别处理，见 `applyTransport` |
| sing-box 对未知字段会报错 | 字段名写错不会静默失效 | 因此"能被它解析成功"是有效断言 |

## 已知限制与后续可做

- **WARP / Hysteria2 的 UDP 在部分网络下可能回落到 TCP**：本地端口的 UDP 能力取决于出口协议
  与前置能力；`http` 与 `wireguard` 出口不支持 UDP。浏览器 QUIC 失败会自动回退 TCP，
  网页浏览不受影响。
- **单节点一个 sing-box 实例的内存开销**：每个出口是一个独立实例（带自己的 router），
  好处是启停互不影响、代价是节点很多（几十个）时会有一点固定开销。
- **没有托盘图标**：Wails v2 不做托盘，本项目也不为此引入 cgo 依赖。
- **界面未做无障碍适配**：这是自用桌面工具，没有做完整的键盘导航与读屏支持。
- **端到端验证的边界**：本机**没有对真实 Reality / Hysteria2 服务器**做端到端连通验证，
  只验证到「生成的配置能被 sing-box 接受 + 实例能启动 + 拨号能发出去」这一层；
  真链式端到端是用**自研 SOCKS5 出口**打通的。

后续可做：

1. 对真实 Reality / Hysteria2 服务器补一次端到端连通验证（需要一台可控服务端）。
2. WireGuard 上游的客户端侧 UDP 转发（浏览器 QUIC / DoUDP 走隧道）—— v1 遗留项，仍未做。
3. 托盘图标常驻、链路健康度曲线。

## 界面微调（第 3 轮，2026-10-11）

两处按使用反馈做的调整，都属于"看着就知道该改、但不动手看不出问题"的那类。

### 1. 列表改通栏，左右不留白

原先表格外面套了一层"卡片"（`margin: 10px 14px 12px` + 边框 + 圆角），
左右各留 14px。改成通栏：`margin: 0`、去掉边框与圆角，表格直接抵到窗口两边。
同时把第一列单元格的左内边距调到 14px，让它和上方筛选栏的左边缘对齐
（否则通栏之后第一列会显得比上面的控件"缩进去一点"）。
上下分隔交给筛选栏的 `border-bottom` 与表头自身的底色。

### 2. 表头支持拖拽调列宽，并保证下限

需求原话是"任意拖拽列宽度，但最小也得保留一个字，不要完全重叠"。
实现过程中翻 Element Plus 源码踩到三个点：

| 发现 | 位置 | 处理 |
|---|---|---|
| 拖拽手柄**要求 `border`**，否则 `handleMouseMove` 直接 return，鼠标在哪都不显示可拖拽光标 | `table-header/event-helper.mjs` `if (!props.border) return` | 给表格加 `border`；再用 CSS 去掉它附带的那圈外框（通栏下多余） |
| 库内部下限**只有 30px** | 同文件 `columnRect.left - tableLeft + 30` | 在 `header-dragend` 里自己钳到 `MIN_COL_WIDTH = 56px`（约两个汉字），并直接改 `column.realWidth` |
| **最后一列默认不可拖** | `allowDragLastColumn` | 显式打开，做到"任意列都能拖" |

为什么改成 `column.realWidth` 而不是只改自己的状态：
`handleMouseUp` 里 `scheduleLayout` 排在下一个 `requestAnimationFrame`，
而 `header-dragend` 是在它**之前**发出的 —— 在这个时机改写，
会被紧接着的那次重排采用，不会先按超窄宽度画一帧（否则会看到一次闪动）。

列宽会**持久化**（localStorage），「列显示」面板底部另加了一个「重置列宽」。

### 验证方式

拖拽这件事本来就"只能手动试"，但没必要真的去动鼠标：
在 `-open resize` 里派发**合成鼠标事件**（`MouseEvent` + 客户端坐标）
走一遍真实代码路径（mousemove 到表头右边缘 → mousedown → 拖 400px → mouseup），
再把测出来的宽度打进一条常驻通知里，从截图直接读数字。实测：

```
别名列：208px → 往左拖 400px 后 56px
        （库内下限 30px，我们钳到 56px；store 记录 = 56）
最后一列「速度(MB/s)」：106px → 56px（验证 allow-drag-last-column）
```

单元格在 56px 下显示为"任..."，即**保住了一个完整汉字 + 省略号**，没有重叠 ——
正是需求要的效果。

## 填充列：右端永远不留白（第 4 轮，2026-10-11）

### 问题

上一轮做完"任意拖拽列宽"之后，用户反馈：缩短某一列时右侧会冒出一条留白，
希望"让最后一列自己占满右侧剩余空间，不要留白"。

### 根因（翻源码才看清）

Element Plus 判断一列是否"弹性"，依据是 `!isNumber(column.width)`
（`table-layout.mjs` 的 `updateColumnsWidth`：

    const flexColumns = flattenColumns.filter((column) => !isNumber(column.width))

而**拖拽结束时会执行 `column.width = column.realWidth = 拖出来的数字`**
（`table-header/event-helper.mjs` 的 `handleMouseUp`）。
上一轮的实现里，唯一的弹性列是"地址"；一旦用户拖过它，它就被固定了，
于是**整个表格不再有弹性列**，总宽小于容器宽，右端就空出一条留白。
之后无论拖哪一列，留白都只会更明显。

### 解决

把**最右边那一列**指定为"填充列"：

  - 它不绑 `width`，只绑 `min-width`（= 用户拖出来的值，或它自己的默认宽度）；
    于是它的实际宽度 = `minWidth + 剩余空间`（`table-layout.mjs` 第 109 行），
    永远铺满右端。
  - 在 `header-dragend` 里把它的 `column.width` 清成 `undefined`，
    让它拖完重新回到弹性状态（紧随的重排由 `min-width` 的 watcher 触发）。
  - 「列显示」里切换可见列时，填充列自动变成当前最右的那一列。

同时把"地址/备注/前置"从弹性列改回普通固定列 —— 免得出现两个弹性列
（那样剩余空间会按 min-width 比例分摊给它们，语义变复杂）。

### 取舍（明确写进界面提示）

在空间还有富余时，**把填充列拖窄看不出变化** —— 这正是用户要的
（"缩短它就让它在剩余空间里自己铺满"）。拖它改的是它的*最小宽度*：
只有当窗口窄到列放不下时，这个下限才会体现出来（触发横向滚动而不是挤成一条线）。
「列显示」面板底部的提示里写明了这一点。

### 验证（数字来自截图里的常驻通知）

`-open resize` 现在会依次做三件事并量出"右侧留白"
（= 表格容器右边缘 − 最后一列表头右边缘，期望 0px）：

    1) 「别名」208px → 往左拖 400px 后 56px（库内下限仅 30px，我们钳到 56px）
    2) 填充列「速度(MB/s)」290px → 拖后再量 290px（松手后回到"占满剩余"）
    3) 右侧留白：拖中间列后 0px，拖填充列后 0px（都应为 0）
    store 记录：{"name":56,"speed":230}

注意第 2 条：拖了 60px 之后**视觉宽度不变**（仍然 290px），
而 store 里记的下限从 116 变成了 230 —— 正是"先改下限、宽度仍由剩余空间决定"的设计。

## 对话框体验调整（第 5 轮，2026-10-11）

四条使用反馈，都改了。

### 1. 添加节点弹窗去掉顶部那两个导入入口

「从剪贴板导入分享链接 / 从屏幕扫描二维码」原本在对话框顶部又放了一份，
和顶栏「导入」菜单重复。删掉区块、对应的两个函数、图标导入与那段样式。
入口统一留在顶栏「导入」菜单里（它还有第三个"手动粘贴链接…"）。

### 2. 弹窗能拖动"飘开"，且不会被边界裁切

用 `<el-dialog draggable>`。关键发现是**它的默认行为就是"能拖但不越界"**：

    hooks/use-draggable/index.mjs 第 25-28 行
    if (!overflow?.value) {
      moveX = clamp(moveX, minLeft, maxLeft)
      moveY = clamp(moveY, minTop, maxTop)
    }

`overflow` 的默认值是假（`props.overflow ?? globalConfig ?? false`），
所以拖动会被钳制在视口内。它的文档注释写的是 "draggable Dialog can overflow
the viewport"，那指的是显式把 `overflow` 设成真的时候 —— 差点被这句话误导。

**"脱离主窗口成为独立窗口"做不到**：Wails v2 没有多窗口 API
（`options.App` 描述的是唯一那个窗口，`pkg/runtime` 只有对这一个窗口的
setter，没有创建新窗口的接口）。要做到真正的独立窗口得换 Wails v3，
或者自己用 COM 托管第二个 WebView2 —— 代价都太大了。
所以这里交付的是"窗口内自由拖动 + 永远不被裁切"。

### 3. 长表单底部按钮不再被窗口裁掉

这是"被边界裁切"的真实主因：VLESS 带 Reality 的表单比窗口还高，
底部那排按钮直接被窗口下边缘切掉。修法是给对话框加高度上限、让 body 内部滚动：

    .el-dialog.cp-dialog { display:flex; flex-direction:column;
                           max-height: calc(96vh - 32px); margin-bottom: 24px; }
    .cp-dialog .el-dialog__body { flex:1 1 auto; min-height:0; overflow-y:auto; }

`min-height: 0` 不能少 —— 默认的 `min-height: auto` 会让 flex 子项被内容撑破，
内部滚动就失效了。

**这里踩了一个 CSS 选择器的坑**：`el-dialog` 上的 `class="cp-dialog"` 是
**透传到 `.el-dialog` 自身**的（不是外面那层 overlay），所以"给对话框本体加样式"
必须写 `.el-dialog.cp-dialog`；我一开始写成 `.cp-dialog .el-dialog`
（祖先-后代）根本匹配不到，表现为"高度上限没生效、底部按钮照样被裁"。
是 `-open dialogdrag` 那条自测通知先报出"找不到对话框"才暴露的。

### 4. 关闭图标与底部按钮做大 + 居中 + 取消改警告色

  - 右上角关闭按钮：命中区域 40x40，图标字号 14px → 20px
  - 底部按钮：高度 24px（全局 size 是 small）→ 36px，最小宽度 112px
  - 底部按钮**居中**（`justify-content: center`）；两个按钮间距仍是 8px
  - 「取消」统一换成 `type="warning"` 警告色（橙）
  - 设置面板那排是"恢复默认设置 + 占位 + 取消 + 保存"，
    `justify-content: center` 配合 `flex:1` 的占位元素后仍然靠右，不受影响

走一遍真实拖拽（`mousedown` 在 `.el-dialog__header` 上，`mousemove/mouseup`

### 修：浮动弹窗拖动时"卡片跟着鼠标跑、松开还黏住"（用户实报）

**现象**：在浮动窗口里按住顶部标题栏拖动，对话框卡片会跟着鼠标位移、
松开后停在鼠标那儿（像黏住），同时窗口内的页面上下滚动；只有拖"关闭图标左边那一段"
才能正常移动窗口。

**根因**：**两套拖动机制同时开着**。
窗口内浮层靠 Element Plus 的 `draggable`（用 `transform` 移动对话框卡片），
浮动窗口靠 v3 的 `--wails-draggable: drag`（移动整个 OS 窗口）——
浮动窗口里两者叠加：卡片被 transform 拖走 + 窗口也在移动。
卡片被移出可视区后自然冒滚动条，于是"窗口不动、页面上下滚"。

**修法**：
- `ui.floatMode` 标记当前窗口是不是浮动对话框窗口，`NodeDialog` 改成
  `:draggable="!ui.floatMode"` —— 浮动模式下由整个窗口负责移动；
- 标题栏加 `user-select: none` / `-webkit-user-drag: none`，
  免得浏览器再掺一脚原生文字选中/元素拖拽。

**回归测试**（两个方向都测，防止修一个坏一个）：

| 自测入口 | 断言 | 结果 |
|---|---|---|
| `-open floatdragtest`（浮动窗口内合成标题栏拖动） | `.el-dialog` 的 inline transform **仍为空**、无横向溢出 | `（空）→（空）`，`是否出现横向溢出 = false` ✓ |
| `-open dialogdrag`（主窗口内的浮层拖动） | 对话框**会**被移动，长表单底部按钮仍完整可见 | `left=104 top=30`（明显偏离居中）、底部按钮 `bottom=655 < 701` ✓ |

### 修（严重）：二维码屏幕圈选一点就崩溃、整个程序消失（用户实报）

**现象**：点「从屏幕扫描二维码」→ 主窗口隐藏了，但遮罩与红色十字准星没立刻出现 →
按住左键拖一下就什么都没有了，**连程序本体也找不到了**。

**根因**：`internal/qrscan/overlay_windows.go` 里 `pTextOutW` 绑在了 **user32** 上，
而 `TextOutW` 实际在 **gdi32** 里。拖动产生选区后，`WM_PAINT` 要画"尺寸标签"时
Go 的 `LazyProc` 找不到这个过程名 → **panic** → panic 发生在窗口过程里 → **整个进程退出**。

抓法：GUI 版没有控制台看不到 panic，改用**带控制台的构建**复现，stderr 里直接给出栈：

    panic: Failed to find TextOutW procedure in user32.dll: The specified procedure could not be found.
      qrscan.(*overlay).paintSelection(overlay_windows.go:1065)
      qrscan.(*overlay).onPaint(...)          ← WM_PAINT
      qrscan.overlayWndProc(...)

**为什么之前 6 个覆盖层测试全绿却没抓到**：那些测试用 `hideOverlayForTest` 让窗口保持
**隐藏**来驱动消息，而隐藏窗口永远收不到 `WM_PAINT` —— 画尺寸标签那条路径从没被执行过。
"测试全绿"和"这条路径没坏"是两件事，这就是活生生的例子。

顺带发现：同一个 var 块里的 `CreateSolidBrush` 早先也犯过同样的错（注释还在），
说明这是**一类**错误，不是一次手误。

**修法（四层）**：

1. 把 `TextOutW` 改绑 `gdi32`；
2. **新增 `TestAllWin32ProcsResolve`**：把包里每一个绑定的过程名都 `Find()` 一遍。
   绑错 DLL 编译期看不出来，但 `Find()` 会当场失败。已反向验证：把绑定改回 user32，
   这个测试立刻红并指出"TextOutW 在 user32 里找不到"；改回来即绿；
3. 在覆盖层会话的 defer 里加 `recover()`：同类问题以后最多让**这一次圈选失败**，
   而不是让整个程序消失（主窗口照常恢复）；
4. 选区小于 12px 按"取消"处理 —— 在遮罩上点一下不拖，本来就是在说"算了"，
   不该丢一个 0x0 矩形去截图/识别。

**验证（带控制台的构建 + 用 PostMessage 驱动真实拖拽，不碰真实鼠标）**：

| | 修复前 | 修复后 |
|---|---|---|
| 拖拽后可见窗口 | **无**（主窗口没回来） | `1180x740 @(370,146) ChainProxy · 链式代理` ✓ |
| 进程 | **已死** | 活着 ✓ |
| stderr | `panic: Failed to find TextOutW …` | 无 panic ✓ |
| 日志选区 | `(0,0)-(0,0)`（错乱） | `(800,400)-(1200,600)`（正确）✓ |

另外给 `cmd/uishot` 增加了 `-postdrag <窗口标题> -rect x,y,w,h`：
向指定窗口投递一组鼠标消息（按下→移动若干步→松开），坐标是屏幕坐标、内部换算成客户区。
它让这条交互路径以后能被自动化验证，而不是只能靠人手动拖。

**还没解决的一点**：遮罩从"主窗口隐藏"到"出现在屏幕上"大约有 1-2 秒空档
（日志：`11:32:12 准备创建` → `11:32:14 已创建`）。用户感知就是"点了没反应"。
下一步要给 capture/建窗/首帧分别计时，找出这 1-2 秒花在哪。

### 功能：全局快捷键可自定义 + 新增设置「快捷键」页（用户要求）

### 修：屏幕圈选"点了要等两秒才出遮罩"（用户实报的"没有立刻显示出来"）

**先量化**：给这条链路每一步加了计时日志，实测

    主窗口已隐藏，准备创建遮罩（288ms）      ← 刻意等窗口真的隐掉
    遮罩已显示 …（建窗耗时 2173ms）          ← 慢在这里

**定位**：怀疑 `disableDragFullWindows()`（它用 `SPIF_SENDCHANGE` 把
`WM_SETTINGCHANGE` 广播给**所有**顶层窗口并等它们响应）。做了个决定性实验：
临时去掉这一句再测 —— **2173ms → 331ms**，确认就是它。

**修法**：不是删掉它（它确实在防拖拽重绘与实时选区重绘打架），而是**改顺序**：
原来它排在"显示窗口"之前，于是"主窗口已隐藏、遮罩还没出现"的空档接近 2 秒。
现在窗口先显示、再发"遮罩已就绪"信号、最后才做这个 1.8 秒的系统设置。

    修改后：遮罩已显示 …（建窗耗时 326ms）   ← 延迟从 ~2.4s 降到 ~0.6s

**顺带修了一个度量错误**：`ready` 信号原本在 `create()` 返回后才发，而那个昂贵调用
排在 `create()` 末尾，所以第一版"移到最后"根本没改善读数（仍是 2137ms）。
把 `disableDragFullWindows` 移出 `create()`、放到 `ready <-` **之后**，
读数才如实等于用户看到的延迟。度量点选错，会让人以为改错了。

### 圈选体验对齐微信/QQ：压暗 + 选区透亮，并把延迟压到 ~75ms（用户要求）

用户原话："点击扫码的时候得卡一会儿才会弄出来十字准星，然后优化下，十字准星出来后
给全屏加半透明遮罩，左键用十字准星画出来的区域再部分取消遮罩，松手的时候取消全部
遮罩然后将主窗口临时提到所有窗口上面，就提一下，不固定。"

**① 延迟：2.4s → 342ms → 75ms。**

先量化（`qrscan.Tracef` 时间线 + 每步计时日志）：

    截屏=33ms  转格式=6ms  建窗+首帧=27ms（合计 66ms）

也就是说遮罩本身只要 66ms —— 剩下的全在**捕获前的那段等待**里。逐次试了三种做法：

| 做法 | 耗时 | 结果 |
|---|---|---|
| `time.Sleep(280ms)` 等窗口隐掉 | 285ms | 能用，但这是整条链路最大的一块，用户明确说"卡一会儿" |
| `WDA_EXCLUDEFROMCAPTURE` 把主窗口从捕获里排除 | 0ms | ❌ 被排除的窗口在 BitBlt 捕获里变成**一块纯黑**，遮罩背景上出现黑色方洞 |
| `Hide()` + `DwmFlush()` 等合成 | 42ms | ❌ DWM 给隐藏窗口做约 200ms **淡出动画**，截到的是动画中间（半透明黑板） |
| **把主窗口挪到屏幕外**（最终采用） | **4-7ms** | ✅ 移动没有动画，位置一变下一帧就是最终状态 |

最后那句 280ms 的等待，其实一直是在**等 DWM 的隐藏动画演完** —— 这是量化之后才看清的。

**② 压暗 + 选区透亮**（`paintDim` + `paintClearSelection`）：
背景先贴整屏截图，再用 msimg32 的 `AlphaBlend` 铺一层 43% 的黑，最后把选区那块
**从原图重贴一次**（不压暗）。顺序不能反 —— 先铺暗色再"挖"出选区。
压暗源用的是一块 **1x1 纯黑位图**靠拉伸铺满：源是纯色，拉伸不失真，
还省掉一整张 16MB 的暗色副本（那样每帧要多跑 400 万像素换算）。

**③ 松手后把主窗口临时提到最前**：`SetWindowPos(HWND_TOP)` + `SetForegroundWindow`，
**不是** `HWND_TOPMOST` —— 用户要的是"提一下，不固定"。
用 `uishot -list` 验证：圈选期间主窗口在 `(-32000,-32000)`，结束后回到原位 `(370,146)`，
且不带 `TOP` 标记（没有留下永久置顶）。

**顺带**：`uishot` 新增 `-postdrag ... -hold`（只按下+移动、不松开），
用来截取"拖拽中间态" —— 没有它就没法验证压暗与选区透亮，
而且这个中间态还帮我发现"主窗口变纯黑"那个问题。

**注意**：验证过程中看到的黑色方洞一度让我以为挪窗口失败了，实际那是**我带控制台的
测试构建的控制台窗口**（1129x635，尺寸正好对上）。正式版 `-H windowsgui` 没有控制台，
用正式产物复测后画面干净 —— 以后做这类视觉验证必须用正式产物，不然会自己骗自己。

### 修：圈选"先出半条线、卡一会儿才响应"（1.8 秒冻结）

用户原话："点击扫描后会只有一个横线，然后卡着一会儿，才有竖线，然后又才能随意拖动。"

**根因**：`disableDragFullWindows()`。它用 `SPIF_SENDCHANGE` 把 `WM_SETTINGCHANGE`
广播给**所有**顶层窗口并等它们响应，**实测 1.8 秒**；而它跑在覆盖层**自己那条消息循环
线程**上 —— 窗口刚显示（第一帧只画了一部分）就被冻住 1.8 秒，期间所有
`WM_PAINT` / `WM_MOUSEMOVE` 全在排队。这正是"半条线 → 卡住 → 才恢复"。

**上一轮之所以没发现**：我把它的调用挪到了"遮罩已就绪"信号**之后**，
于是计时日志里看不到它（84ms），但它照样冻结界面 —— **信号发得早 ≠ 界面不卡**。

**处理：直接删掉**。理由：
- 它想防的"拖拽全窗口重绘与实时选区重绘打架"**没有实测证据**；
- 代价是一个冻结的窗口；
- 而且它用 `SPIF_UPDATEINIFILE` **改动了用户的全局系统偏好**（会写进注册表），
  一个截图工具不该动这个。

**顺带把绘制改成严格 1:1**：`paintScreen` 原先"把源图拉伸铺满客户区"，
而 `paintClearSelection` 是 1:1 拷贝 —— 只要客户区尺寸 ≠ 截图尺寸（DPI 缩放就会出现），
两种映射就不一致，表现为"挖出来的选区跟背景对不上"。
现在两处都用源尺寸。**实测你这台机器两者本来就相等**
（`客户区=3840x1080 截图=3840x1080`），所以它不是当前错位的成因，属于防御性修正。

### 未解决：选区内容与背景"上下错位"

用户实报："画出来的部分分辨率似乎有问题，和原本的内容有上下错位"。
我用正式产物 + 合成拖拽复现到了这个现象（选区内的文字与同一水平位置的外部文字
不是同一行）。但**当前的手段不足以精确定位**，两个干扰：

1. 我带控制台的测试构建会显示一个**黑色控制台窗口**，它一度让"选区内容发黑"
   这个读数完全失真 —— 视觉验证必须用正式产物；
2. 合成拖拽存在**时序假象**：十字准星的横线停在倒数第二步的鼠标位置
   （第 5 步 y=593，最后一步 680），说明我截图时最后一条移动消息的绘制还没发生。
   用这种方式量偏移量不可靠。

**下一步方案（也是用户建议的方向：照微信/QQ 的做法）**：
现在的实现是"把整屏截图贴到一块画布上、再自己算坐标挖出选区"，
坐标一needs对不上就错位。改成**让窗口系统来保证对齐**：

- **压暗层**：整屏 `WS_EX_LAYERED` + `SetLayeredWindowAttributes(alpha)` 的半透明黑窗口
  —— 根本不需要截图当背景，压暗是窗口属性给的；
- **选区"挖洞"**：用 `SetWindowRgn` 把压暗层的区域设成"整屏减去选区"，
  选区那块自然漏出**真实的、未压暗的桌面** —— 对齐由窗口管理器保证，
  没有任何坐标换算，也就不可能错位；
- **装饰层**：再叠一个 `LWA_COLORKEY` 的窗口画十字准星/边框/尺寸标签
  （颜色键做透明，线条仍是实心红），并设 `WS_EX_TRANSPARENT` 让鼠标穿透。

这样"截图"只用于最后识别，不再参与显示，整类错位问题从结构上消失。

### 圈选覆盖层改结构：半透明压暗层 + 窗口区域挖洞（根治错位）

用户实报"截图区域偏移"（对照文字：同一批文件夹名在选区内外相差约 30px）。
我把像素层面的假设逐个验证，**全部被数据否掉**：

| 假设 | 实测 | 结论 |
|---|---|---|
| 客户区 ≠ 截图尺寸（拉伸错位） | `客户区=3840x1080 截图=3840x1080` | ❌ |
| 缓冲区长度不对 | `bgra=16588800 期望=16588800` | ❌ |
| 行距（Stride）错位导致斜切 | `源图 stride=15360 期望=15360` | ❌ |
| 两条绘制路径映射不同 | 都是 src(x,y)→dst(x,y) 1:1 | ❌ |

**连续几轮新测量都在推翻上一个假设 —— 说明"贴整屏截图 + 自己算坐标挖选区"这条路本身就不该走。**

**改成让窗口系统保证对齐**：

  - **压暗层**：窗口加 `WS_EX_LAYERED` + `SetLayeredWindowAttributes(alpha=110)`，
    背景只铺纯黑。"黑 + 半透明"就是整屏压暗，**不需要截图当背景**；
  - **选区挖洞**：`SetWindowRgn` 把窗口区域设成"整屏减去选区（内缩一个边框宽）"，
    选区那块不再被窗口覆盖 → 漏出**真实的、未压暗的桌面**。
    对齐由窗口管理器保证，**显示环节完全不碰像素**，这类错位从结构上消失；
  - 拖动期间靠 `SetCapture` 保证鼠标消息仍归我们（洞口不覆盖鼠标）。

**顺带**：显示不再需要截图，于是把"预先截整屏"整个删掉 —— 时间线从
`截屏=33ms 转格式=6ms 建窗+首帧=27ms` 变成 `截屏=0ms 转格式=0ms 建窗+首帧=29ms`，
**点击到出遮罩从 2.4 秒一路降到 35ms**。

**测试帮我抓到一个真缺陷**：`newOverlay(vs, nil)` 最初没做 nil 保护 → 空指针 panic；
而 panic 发生在 `ready` 信号**之前**，于是 `SelectRegionHooked` 永久卡在 `<-ready` 上
（5 个覆盖层测试同时超时、日志停在"准备创建遮罩"）。
除了补 nil 保护，还加了"**就绪前 panic 也必须叫醒调用方**"：
defer 里若尚未发过 ready，就补发一个错误。这类"失败但不通知"的挂死最难查。

**验收**（正式产物 + 合成拖拽的中间态截图）：选区内是原亮度的真实桌面，
选区外压暗，**上下边界处文字连续、无错位无重复**；
时刻线 `建窗+首帧=29ms`、`遮罩已显示（35ms）`；全量测试 8 个包全过。

**遗留（下一步清理）**：`paintScreen` / `paintDim` / `paintClearSelection` 与
`bgra`/`bmi`/`dimDC` 等字段已经没人用了（Go 允许未使用的函数/字段，所以不影响编译），
下一轮统一删除，别让死代码留着误导人。

### 功能：底部栏目（第 2 步：流量统计）

用户对这块的原话："其实就是主流客户端里面首页这里的流量统计板块，只不过我们要做到
我们这里然后铺开，毕竟我们窗口是宽度优势"。

**先把后端缺的那一环补上**：`internal/app/stats.go` 每秒本来就在算每个节点的增量
（`dUp/dDown`），但**算完就扔了** —— 既没有速率、也没有历史。补了三样：

  - `Summary.UpRate/DownRate`：最近一秒的总速率（字节/秒），用原子量存，
    `Summary()` 这种不加锁的读取也能安全拿到；
  - `App.traffic`：每秒一个样本的环形缓冲（保留 1 小时，约 86KB），
    裁掉超出部分的那段算术单独抽成 `pushTrafficLocked` 才**测得到** ——
    它只在连续跑满一小时之后才生效，靠等是等不到的；
  - `Summary.MemMB`：进程内存占用。用 Go 运行时的数字而不是 Win32 工作集，
    因为内核（sing-box）跑在**本进程里**、界面在另一个 WebView2 进程里，
    这个数恰好对应主流客户端界面上那个"内核占用"。

**界面**（`components/bottom/TrafficView.vue`）：左侧曲线（上传/下载双线 + 面积，
共用同一个纵轴上限，否则上下行没法比）+ `1分钟/10分钟/1小时`；右侧六个指标格 +
**按节点流量排行**（前 5 名，带比例条）。

**两个刻意的取舍**：

  1. **历史留在 Go 侧，不让界面自己攒** —— 界面的刷新是去抖合并的（store 的
     `scheduleRefresh`），拿到的样本时间间隔不规则，画曲线没有意义。
  2. **轮询间隔按范围给**（1分钟→2s、10分钟→3s、1小时→10s）：为了看 1 小时的曲线
     每 2 秒搬 3600 个样本不值得。

**验收**：通过本地节点打真实流量（curl 走 socks5h://127.0.0.1:10810/10811），
曲线出现对应的三座峰、峰值 1.69 MB/s；排行里两个节点各自的总量与比例条都对；
状态区显示 `↑ 0 KB ↓ 561 KB`；指标格与顶部工具栏的数字互相一致。
测试打进去的今日流量已清零，没有留在用户配置里。

### 功能：底部栏目（第 3 步：网络日志）

**先说一个走错的路，因为它值得记下来**：按原计划，网络日志要在内嵌 sing-box 的 `log`
上挂 writer 来拿连接流水。做完之后**一条都没有**。翻 sing-box 源码才明白：

  - 我们的 sing-box 只当**出口**用，**没有 inbound**；
  - 而且是直接调 outbound 的 `DialContext`、**绕过了它的路由器**；
  - 那条 `outbound connection to ...` 是**路由器**在路由时才打的日志。

也就是说：这条路无论把级别调到多低都不会有数据。
（顺带确认了一件事：只要挂了 platform writer，sing-box 的 `observableLogger` 就
**不再按级别提前返回**，所以 writer 收到的是全部级别 —— 级别配置只影响它自己的控制台输出。）

**改成接我们自己的 handler**：`internal/proxy/connlog.go` 新增 `ConnEvent{Node, Protocol, Target}`
与进程级接收器 `SetConnLogSink`，在 SOCKS5 / HTTP CONNECT / UDP ASSOCIATE 三个建立点上报。
它早就知道"谁连了哪儿"（`handler.go` 里本来就在打"隧道建立 → 目标"），只是那些信息
以前混在用户日志里。

**链路**：handler → `app.appendNetworkLog` → 环形缓冲（2000 条、自增序号）→
`GetNetworkLogs(afterSeq)` → 界面**游标式增量拉取**（每秒可能十几条，每次重传整段不可接受）。

**界面**：日志视图左侧的「网络日志」页签启用；过滤器 / 清除本项 / 自动滚动**对当前页签生效**
（用户明确要的："清除本项（即点击后清除现在展示的用户日志 / 网络日志）"）。
网络日志按流水格式展示：`HH:MM:SS [节点] 协议 → 目标`。

**验证**：通过两个节点各打若干真实连接，网络日志出现

    05:21:57 [住宅代理1] socks5 → www.github.com:443
    05:22:00 [住宅代理2] socks5 → www.apple.com:443

六条，节点归属与时间都对。另有 4 个单元测试锁死游标语义（含**裁剪之后旧游标仍要返回
全部保留项**、以及**清空后序号继续递增**这两个边界）。

### 功能：底部栏目（第 4 步：网站测试 + 我的 IP 信息 + 可达性矩阵）

**国名不硬编码**：ipinfo 只给 `CN` 这种码，中文国名交给前端的
`Intl.DisplayNames(['zh-CN'], {type:'region'})` —— 不维护"码→名"映射表（那种表一定会过期）。
国家图标用**国家码小徽章**：Windows 不渲染国旗 emoji（会显示成两个字母），
与其放一个显示不出来的图标，不如就显示码本身。

**"本机自己的 IP"这条要特别小心**：用户明确要的是本机直连 IP，不是出口 IP。
所以这个请求的 `http.Transport` **显式设 `Proxy: nil`** ——
默认的 `ProxyFromEnvironment` 一旦被系统代理带走，拿回来的就是节点出口 IP，与需求正好相反。
实测显示的 `27.186.•••.•••` 与直连 curl 的结果一致，说明这一条生效了。
IP 默认脱敏（保留前两段），旁边眼睛点击显示完整。

**站点测试**：`internal/proxy/socksclient.go` 自己实现了 SOCKS5 客户端（约 90 行），
走**节点的本地监听口** —— 和浏览器走的完全同一条路（本地口 → 前置 → 出口），
测出来的才是用户真正会遇到的延迟。节点之间并行、同节点内串行。
接口只取前 2KB（Range），测的是连通性不是带宽。

**顺带把矩阵做出来了**：后端返回的就是"站点 × 节点"的结果，所以列表和矩阵是同一份数据的
两种展示，切"矩阵"开关就切视图。

**验证**（打真实站点，两种视图都验过）：

    列表：Apple 3912ms ✓  Google 3200ms ✓  YouTube 3658ms ✓  GitHub 超时（红，写明原因）

    矩阵：站点      住宅代理1   住宅代理2
          Apple     ×          3157ms
          GitHub    ×          ×
          Google    3843ms     3025ms
          YouTube   ×          3217ms

矩阵立刻看出：**住宅代理1 上 Apple/YouTube 都不通，住宅代理2 全都通** —— 这正是它的用途。

**截图抓到一个真 bug**：矩阵开关点不动。原因是 `el-switch` 已经用 `v-model` 改了值，
我又在 `@change` 里**再翻转一次**，两次抵消 —— 开关看着弹回去。改成 `watch` 做持久化与清结果。
（这类"双写"错误肉眼很难看出来，是截图的"开关还是灰的 + 结果只有 4 条"露的马脚。）

另有 5 个单元测试锁死 SOCKS5 客户端**实际发出的字节**（版本/命令/地址类型/端口大端序），
以及分片应答、拒绝码、IPv4 目标、非法目标 —— 协议字节写错在生产里只会表现为
"测试一直失败"，看不出原因。

### 功能：底部栏目（第 5 步：连接）

**又是同一个坑**：计划里写的是"启用 sing-box 的 内核自带的 RESTful API 取连接"。但我们的 sing-box
只当出口用、**且绕过了它的路由器** —— 它的连接列表里永远不会有东西（第 3 步在日志上
已经踩过一次）。所以这一版**建立在自己的 handler 上**：`ConnEvent` 从"只报建立"
扩展成**连接生命周期**（open / close），close 带上双向字节与时长。

**做法**：

  - `relay.go` 的 `Relay` 现在返回 **(上行, 下行) 字节**。它的拷贝循环里本来就在累加
    全局统计，顺手带回来即可 —— 不必为了计数再包一层连接包装器（那会丢掉底层读写优化）。
  - `proxy/connlog.go` 新增**活动连接登记**：登记时就记下这条连接的参与者
    （客户端连接 + 远端连接），"关闭全部"才有东西可关；不然那个按钮只能是个摆设。
  - **实时字节**：`ConnCounter` 由中继循环直接累加，界面按秒轮询时读一次。
    最初的实现只在连接**结束**时回传字节 —— 于是正在传输的连接上下行一直显示 0，
    看不出它是否在动（自测截图抓到了这一点）。
  - `app` 维护连接表（活动 + 最近关闭 200 条），`desktop` 暴露 `GetConnections` /
    `CloseAllConnections`。

**两处刻意的取舍**：

  1. **没有"规则"这一列**：我们不做规则分流（没有规则引擎），与其放一个永远空的列，不如不放；
  2. **UDP 不进连接表**：它没有 Relay 那样的双向字节统计，登记进去只会显示假数字 ——
     UDP 仍然进网络日志。

**验收**（端到端，不是看空表）：

  - 起一个 40MB 的真实下载：连接表出现
    `speed.cloudflare.com:443 | socks5 | 住宅代理1 | 源端口 13395 | 时长 8.0s | 上传 0.66 KB | 下载 4.05 MB`，
    与顶部工具栏的流量、活动连接数互相一致；
  - 点「关闭全部」后：`活跃 0 | 已关闭 1`，归档行保留了最终字节与时长
    （`2.2s | 0.66 KB | 2.79 MB`），**curl 以退出码 56 中断**（接收数据失败）——
    证明连接是**真被掐断**的，而不是"只从列表里删掉"。

**测试又抓到一个真问题**：`CloseConnections` 原来只关底层连接、**不摘登记项** ——
"关闭全部"之后活动列表还是满的，用户会以为没关掉。改成关闭的同时立刻摘掉登记项
（真正收尾随后发生，届时 finish 回调补发 close 事件，delete 一个不存在的键无害）。
新增 3 个 app 侧测试（生命周期 / 未知 ID / 已关闭列表裁剪）与 2 个 proxy 侧测试
（关闭真的会关底层 / 两个阶段的事件都发出来）。

按契约把**已有**的网络项从设置弹窗**搬**进面板（是搬家不是复制：同一件事有两个入口，

    （`端口起始值 240 非法（应在 1024-65535 之间）`），面板把错误显示出来、
    **没有把非法值写进配置** —— 这条比我本来要验的成功路径更有价值；
  - 设置弹窗里原位置已是指路行，链接可点。

管不到前端 —— 现在补上 vite 构建（Vue 侧的笔误只有在构建时才暴露）。

### 功能：底部栏目（第 7 步：14 处说明小字瘦身）+ 状态区错误徽标

**逐条判断，不是一刀切**（用户从第 4 轮就点名："设置弹窗里面那一堆多余的赘述的小描述"）：

| 处理 | 处数 | 依据 |
|---|---|---|
| 转成 tooltip（`?` 入口） | 10 | 有真实信息：默认值、使用关系、副作用、约束 |
| 删除 | 1 | 只是把标签换个说法（"启动时自动激活"下面的"自动激活上次处于激活状态的节点"） |
| 保留并压缩 | 3 | 快捷键页的一行说明、冲突警告（真警告）、关于页那段（关于页本来就该有文字） |

**`?` 的位置是改了两遍才对**：第一版把 tooltip 图标放在原说明文字的位置 —— 而那些文字在
很多地方是**分组说明**（在整组字段之后或在表单之前），于是 `?` 变成孤零零一行。
正确的做法是按它解释的对象归位：**字段级**贴控件旁、**分组级**贴分组标题、
**折叠项**用 `el-collapse-item` 的 `#title` 插槽。

顺带踩到两个小坑：WireGuard 的分组标题里**还有一个按钮**（生成密钥），
所以不能用"标题…</div>"来定位；以及我自己写替换串时把一段插了**两份**（清点时发现 ? 比预期多一个）。

**补做目标里漏掉的一项**：头部状态区的**错误徽标**。原先只做了本地端口 / 前置状态 /
实时速率，漏了它。现在用后端已有的 `Summary.Error`（启动失败的节点数）：
**只在真有错误时出现**（平时不占视线），红色，点一下跳到日志视图（原因在那里）。

**验收**：临时插一个"故意连不上"的节点 → 状态区出现红色 `错误 1`，该节点在表里是红点、
节点计数 2/3 ✓（验完已把临时节点从配置里删除）。

**这一轮之后，`docs/BOTTOM_PANEL.md` 的施工清单全部勾完。**

### 关于目标里那两条"引擎改造"的实际做法（与计划不同，有据可查）

  1. **网络日志**：计划是"把内嵌 sing-box 的 log 接到环形缓冲"。实测**拿不到数据** ——
     我们的 sing-box 只当出口、没有 inbound，且绕过它的路由器直连 outbound，
     那条连接流水是路由器在路由时才打的（第 3 步详述）。改由**我们自己的 handler** 上报。
  2. **连接视图**：计划是"启用 内核自带的 RESTful API 取连接与逐连接流量"。同理不适用 ——
     绕过路由器就进不了它的连接表。改由 handler 上报**连接生命周期**
     （建立/结束 + 双向字节 + 时长 + 可关闭），比 内核自带的 RESTful API 更贴合本项目的架构。

功能目标（网络日志、连接表与逐连接流量）都达成了，只是数据来源换成了自己的实现。

### 改进：流量曲线（节点下拉 + 坐标系 + 平滑）+ 一批浮动窗口问题

用户实测反馈后的一轮。

**① 浮动窗口里渲染出底栏（"绿点和两个端口号"）—— 真 bug**
`body.cp-float-window` 的隐藏清单只列了 `.cp-toolbar/.cp-filterbar/.cp-table-wrap`，
**后来新加的 `.cp-bottom` 漏了**。用户说"虽然感觉有点扯，但是我绝对没看错" —— 他没看错。

**② 标题栏"没到顶"—— 用像素定位**
逐像素扫描：改动前 y=0..10 是纯白，之后才是标题栏 → 标题栏上方压着约 14px 的
**对话框内边距**。给浮动模式的 `.cp-dialog` 加 `padding: 0` 后：

    y=0..32  (244,245,247)  ← 标题栏，紧贴窗口顶边
    y=33     (229,231,235)  ← 分隔线
    y=34+    白色           ← 正文

配色同时从 `--cp-panel-2`(#fafbfc) 换成 `--cp-bg`(#f4f5f7)：亮色下前者与正文
(#ffffff) 几乎同色，这就是"区分不明显"的来源。

**③ 每次打开都居中**：原先是从主窗口左上角偏移；改成居中（`-list` 实测
浮动窗口 @(550,176)，主窗口 @(370,146) 1180x740 → 居中正是 (550,176)）。
并且**复用窗口时复位位置**（窗口是复用的，不 `SetPosition` 就会停在上次关闭处）。

**④ 展开/收起按钮**加宽并带汉字；**⑤ 日志**改成 `pre-wrap` + 条目间 5px 间距
（用户："换行的两行也算一行"，所以间距只加在条目之间）。

**⑥ 流量曲线重做**（用户："审美有点弱"）：

  - **按节点的历史**：后端新增 `trafficByNode`（每节点一条 1 小时环形缓冲，约 86KB），
    `TrafficHistory(seconds, nodeID)`；采样时**遍历配置里的所有节点**写样本，
    这样各节点序列按同一节拍推进、切节点看时横轴才对得上。删节点时清掉它的历史。
  - **节点下拉**：位置按用户要求 —— 网速（纵轴上限）往左，下拉夹在它和
    `1分钟/10分钟/1小时` 之间，默认"全部节点"。
  - **坐标系**：Y 轴三档刻度（上限取整到 1/2/5×10ⁿ，免得出现 1.37M 这种）+ 虚线网格 +
    底部时间标签。画法参考了主流客户端的开源实现
    （`refs/local-refs/.../同类实现`，它是手写 canvas：
    `getYAxisTicks` 三档、`LINE_WIDTH_GRID` 虚线、`PADDING_BOTTOM` 留时间轴、
    `chartStyle: 'bezier'` 平滑）。
  - **bezier 平滑**（Catmull-Rom → 三次贝塞尔）治"峰谷太硬"。
  - 用 SVG 画，**画布尺寸跟着容器走**（ResizeObserver，1:1 渲染）——
    `preserveAspectRatio="none"` 拉伸会把文字也拉变形。

**验证**：打真实流量（两个节点各若干批 curl），曲线出现对应峰谷、Y 轴 `4.8M/2.4M/0`
与虚线网格、横轴时间标签；下拉展开后三个选项（全部节点 + 两个节点）都在。
后端另有单测锁死"按节点取历史、互不串台、不存在的节点返回空"。

**顺带修**：时间标签原本按"用户选的时长"格式化 —— 程序刚启动只有几十秒数据时，
即便选 10 分钟，四个标签会全是同一个 `hh:mm`（自测截图里就是四个 07:08）。
改成按**真实跨度**选格式（跨度 < 2 分钟用 mm:ss）。

**两个我自己的失误**：打补丁时对 `styles.css` 的三处改动忘了 `save()`（后面又 `load()` 了
同一文件，把前三处丢弃，只有第四处落盘）；验证白条时像素脚本里**硬编码了旧截图文件名** ——
于是"修复前后"量的是同一张图，得出"没生效"的错误结论。
现在改完一律**回读文件校验**，量之前确认量的是刚生成的那张图。
